# ADR-0027 — Forgot/reset password: anti-enumeration, token model, and concurrency

- Status: Accepted
- Date: 2026-09-11
- Deciders: project owner

## Context

Issue #79 (BR-13) adds self-service password reset for any role — no admin/DB intervention needed. This is a genuine "auth mechanism" decision per `CLAUDE.md` §4 (an unauthenticated, security-sensitive flow with lasting consequences), so it gets its own ADR rather than being decided silently inside the ticket's implementation. It was initially shipped (PR #81) without one; this ADR was written as a review follow-up once the timing-side-channel and concurrency tradeoffs below turned out to need explicit tradeoff records, not just BR-13's prose.

Three questions had to be settled:

1. **Anti-enumeration.** `POST /auth/forgot-password { email }` must not let a caller learn whether an email address has an account — a generic response either way. The response _body_ is trivial to make identical; the harder part is that responding to a known email costs more server-side work (issuing/persisting a token, queuing an email) than responding to an unknown one (a single failed lookup), which can leak through response _timing_ even with an identical body.
2. **Token storage/rotation model.** BR-13 requires "only one active token per account" — a new request invalidates any still-live one. The naive implementation (`deleteMany` then `create`) is two separate statements, which is not atomic: two concurrent requests for the same account can each see zero rows to delete, then both insert, leaving two live tokens.
3. **Reset consumption.** A token must be single-use. Checking validity (`findUnique` + expiry) and then deleting it in a later step leaves a TOCTOU window: two concurrent resets with the same token can both pass the check before either deletes the row.

## Decision

- **Anti-enumeration, two layers.** The outbound reset email is never awaited on the known-email path (`void this.sendMail(...)` in `AuthService.forgotPassword()`) — awaiting a real Scaleway TEM call would be the single largest, most variable timing cost, and it's also unnecessary to await since delivery failure is already a fire-and-forget concern under ADR-0026. On top of that, the whole response is padded to a fixed floor (`FORGOT_PASSWORD_MIN_RESPONSE_MS`, 150 ms) via `Promise.all([realWork, sleep(150)])`, so the one remaining differential — a known email costs one extra DB statement (the upsert) versus a bare lookup for an unknown one — is dominated by the floor rather than visible in response time. This is deliberately a practical mitigation, not a cryptographic guarantee: a floor bounds the _visible_ gap to noise level for a normal HTTP client, it does not make the two code paths literally constant-time.
- **Token storage: one row per account, enforced at the database.** `PasswordResetToken.userId` is `@unique` (not just indexed), and `forgotPassword()` reissues a token via a single `upsert` keyed on `userId` instead of `deleteMany` + `create`. This is the same "in-place update on a unique key, never a second row" pattern ADR-0014 already established for `ReferentAssignment` reassignment. Atomicity comes from Postgres's `ON CONFLICT` handling inside the single upsert statement — two concurrent requests for the same account cannot both survive as distinct rows, because the second one's `ON CONFLICT` branch updates the first's row instead of inserting alongside it.
- **Reset consumption: delete-as-claim inside the transaction.** `resetPassword()` still does an initial `findUnique` + expiry check outside the transaction as a fast-fail for an obviously invalid/expired/unknown token (avoids paying for a `bcrypt.hash` and opening a transaction for garbage input), but that check is not the authority. The actual claim is `tx.passwordResetToken.deleteMany({ where: { id, expiresAt: { gt: now } } })` inside the transaction; if `count === 0`, the transaction throws the same generic `BadRequestException` used for every other invalid-token case. A concurrent second request racing on the same token sees the row already gone (Postgres serializes the two `DELETE`s via the row lock) and gets the documented 400, not an unhandled `P2025` surfacing as a generic 404.
- **Session revocation on a successful reset is RefreshToken-only, not access-token-only.** `resetPassword()` deletes every `RefreshToken` row for the account (same table/pattern ADR-0018 established), forcing every device to log in again to get a new session. It does **not** invalidate an access token already issued: `JwtStrategy` checks only signature/expiry, no DB lookup (ADR-0018's whole point was a stateless access token), so a JWT signed before the reset keeps working for up to its own TTL (`JWT_ACCESS_TTL`, 15 minutes by default). This is accepted as a known, documented gap rather than solved here — see Consequences.

## Consequences

- The 150 ms floor is a fixed cost on every `forgot-password` call, known and unknown email alike. Negligible for a human filling out a form; would matter if this endpoint needed to sustain high throughput, which it doesn't (self-service password reset is inherently low-volume).
- The `userId` unique constraint means `PasswordResetToken` can never hold more than one live row per user by construction — a second `forgotPassword()` call always reissues in place, never accumulates.
- Immediately revoking an access token already issued at the moment of reset is out of scope: doing so would require moving access-token validation from stateless signature checking to a DB-backed revocation list, undoing ADR-0018's short-lived-stateless-JWT design for a case (an attacker who already holds a live access token _and_ triggers a reset) that's already narrower than the more common threat (attacker only has the password). Revisit only if a real incident or a stricter requirement makes the 15-minute window unacceptable.
- `MailerService.sendSafely()` (the shared catch-log-don't-propagate wrapper, review follow-up on PR #81) is what both `AuthService` and `AdminStudentsService` now call — this ADR doesn't re-litigate ADR-0026's mailer boundary, just notes that BR-13 is the second real consumer ADR-0026 anticipated when it deferred a shared abstraction.

## Alternatives considered

- **No timing mitigation at all, response body identity only.** Simplest, but leaves a real (if narrow) enumeration channel open on an unauthenticated endpoint — rejected once the residual DB-round-trip gap was identified in review.
- **Constant-time padding via a dummy DB write on the unknown-email path instead of a fixed sleep.** Would need a fake, non-FK-constrained write target or a no-op query of matching cost — more complex than a fixed floor for a benefit (slightly more "realistic" timing shape) that doesn't matter against ordinary network/HTTP jitter. Rejected as disproportionate.
- **`deleteMany` + `create` wrapped in a `$transaction` instead of `upsert` + a unique constraint.** Wrapping the existing two statements in a transaction reduces but does not eliminate the race under READ COMMITTED (two transactions can each see zero rows to delete before either commits) — only a real constraint enforced by the database closes it. Rejected as an incomplete fix.
- **Full constant-time/timing-safe cryptographic response (e.g. always doing an equivalent bcrypt-cost operation on both paths).** This project's threat model (a low-volume, non-financial university internship system) doesn't justify that complexity; the fixed-floor mitigation above is judged proportionate.
